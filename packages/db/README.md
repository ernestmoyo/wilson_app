# @wilson/db

Postgres schema for the Assure Safety compliance platform. Derives from `docs/GRAPH.md`.

Every column that exists because a regulation demands it names its clause. Every constraint encodes a rule a spreadsheet cannot enforce — which is most of the value of moving off one.

## Migrations

```
001_template_layer.sql     generated by packages/checksheets (npm run gen)
002_instance_layer.sql     clients, jobs, inspections, findings, evidence, certificates
003_guards_and_events.sql  state machine, retention, immutability, append-only audit log
```

Run them in order. `001` is generated — never hand-edit it.

```bash
npm test -w packages/db     # runs every migration against real Postgres, then the guards
```

## No extensions required

The schema deliberately depends on **no Postgres extensions**:

- case-insensitive email uniqueness uses a `lower()` unique index, not `citext`
- the audit hash chain uses built-in `sha256()` (Postgres 11+), not `pgcrypto`

That keeps it portable to any managed Postgres — DigitalOcean, Neon, RDS, or a plain box — which is the property that stops the hosting vendor becoming an architectural decision.

## What the database enforces

| Rule | Clause | Mechanism |
|---|---|---|
| A non-compliance must state why it failed | IPS 21(1)(f) | CHECK on `finding` |
| The result of each item is recorded | IPS 21(1)(c) | `finding.status` enum — replaces the workbook's font colour |
| How each item was verified | IPS 21(1)(e) | `finding.verification_method` |
| Equipment used, per inspection | IPS 21(1)(d) | `inspection.equipment_used`, non-blank |
| Who inspected, and whether supervised | IPS 21(1)(g) | CHECK on `inspection` |
| Photographer name, **occupation**, date, place | IPS 21(4) | CHECK on `evidence`, gated by `provenance` |
| Every communication with the applicant | IPS 21(2)(a) | `communication` table |
| A register of interests | IPS 23(1)–(3) | `interest_declaration`, required before issuance |
| Retention = expiry + 5 years | IPS 21(6) | computed by trigger into `retention_clock` |
| Certificate number prefixed with the authorisation number | IPS 8(1)(c)(ii) | trigger, unless a register number is present |
| WorkSafe register deadline | reg 6.22(5) | defaulted from issue date |
| No grant with pending or unreasoned items | reg 13.39 | `assert_can_issue_certificate()` |
| Conditional certificate must carry conditions | reg 6.24 | CHECK |
| Refusal must state what was not met | reg 6.23(2) | CHECK |
| Legal stage transitions only | Process Flow §1–8 | `job_stage_allowed()` + trigger |
| Published templates are immutable | IPS 21 | trigger on `checksheet_template` |
| Audit log cannot be edited or deleted | IPS 21, 22 | append-only trigger + hash chain |

`verify_event_chain()` returns no rows when the audit log is intact. Run it before producing records for a WorkSafe audit — altering any row breaks every hash after it.

## Two bugs the tests caught

Constraints that have never been executed are decoration. Running them found both of these:

**1. `array_length('{}', 1)` is `NULL`, not `0`.** A CHECK constraint only fails on `FALSE`, so

```sql
CHECK (decision <> 'conditional' OR array_length(conditions, 1) > 0)   -- silently inert
```

accepted a conditional certificate with **no conditions**, and a refusal with **no stated reasons**. `cardinality()` returns 0 for an empty array and is the correct function.

**2. A BEFORE INSERT trigger cannot reference its own row.** `certificate_on_insert` created the `retention_clock` row with `certificate_id = NEW.id` before the certificate existed, so the foreign key had nothing to point at. Retention creation belongs in the AFTER trigger.

Both would have shipped silently. This is why `npm test` runs the real thing rather than checking the SQL parses.

## Testing without a server

Tests run against [PGlite](https://github.com/electric-sql/pglite) — real Postgres compiled to WASM, in-process. No Docker, no daemon, no port, ~200 MB of memory. The same migrations are what deploy to DigitalOcean; nothing about the schema is PGlite-specific.

## Live end-to-end test

`npm run test:e2e` runs the **real G2 Chiller / Argenta job** through the real schema — the actual client record, the actual 54 findings with the statuses recovered from font colour, the actual 11-object evidence manifest, and the actual certificate — walked through all eight process-flow stages twice: once as the workbook stands, and again after remediation.

Both halves matter. A system that only ever says no is useless.

### What it found in the production workbook

Running it surfaced four things a spreadsheet cannot tell you:

1. **One class 6 & 8 item was never assessed.** `reg 13.39` blocked issuance until it was.
2. **Four unresolved non-compliances** — Signage #4, Signage #5, ERP #10, ERP #12 — carried through with their reasons intact.
3. **Eight evidence images carry no IPS 21(4) provenance.** No photographer, occupation, date or place. They are stored as `provenance = 'migrated'` so the gap is visible in the data rather than hidden behind nulls.
4. **The workbook contradicts itself.** The class 6 & 8 sheet records *"compliance certificate refused to be issued"* with two reasons, while the Certificate sheet in the same file shows a **granted** certificate with *"Location Requirements Not Met: None"*.

Point 4 needs Bryan's answer before any of this is relied on. Either the certificate was issued after remediation and the check sheet was never updated, or the two disagree. Both are recoverable; neither should be silent.

### The happy path

After assessing the pending item, raising corrective actions against all four non-compliances and re-verifying them (naming the verifier, which the schema requires), the certificate issues cleanly:

```
CER-0250-166217 / LC/26-250-004
retain until 2034-07-04 (expiry_plus_5y), stamped on all 11 evidence objects
register with WorkSafe by 2026-07-25
7 recorded transitions: application → document_review → site_inspection →
  compliance_evaluation → final_validation → certificate_issued → monitoring
audit chain: intact
```
